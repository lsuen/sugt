# AGENTS.md — guidance for coding agents working on SUGT

## Product snapshot

SUGT is a local AI gateway + skills console (Tauri 2 + React + Rust/Axum). Prefer small, reversible changes. Do not invent private packaging scripts or closed-source paths.

## Theme system (skins)

**Goal:** lightweight, file-per-theme, importable packs — never a God-token CSS file.

### Rules

1. **Contract is fixed** in `src/theme/schema.ts` (`THEME_TOKEN_KEYS`, ~40 keys). Do not add variant tokens (`*-2`, `*-3`, `*-pink`).
2. **One theme = one CSS file** under `src/theme/themes/<id>.css`, or a pack folder `src/theme/packs/<id>/` (`theme.json` + assets + optional `theme.css`). Theme selectors must be `:root[data-theme="<id>"]` (not bare `[data-theme]`), or default `:root` tokens win.
3. **Register** builtins only in `src/theme/registry.ts`. Add zh/en labels in `src/i18n.ts`.
4. **Components** consume `var(--*)` via `src/theme/shell-theme.css` / `src/styles.css`. Never hardcode brand colors in new UI. Never write `[data-theme="x"] .BusinessClass` override blocks.
5. **Background / glass** use `--bg-image`, `--bg-image-opacity`, translucent `--surface*`, and `--glass-blur` (set `0px` to disable).
6. **External packs** are **JSON** (`theme.json`, `version: 1`). Not YAML/TOML. Loader: `src/theme/loadThemePack.ts`.
7. **Docs:** `docs/THEME_AUTHORING.md` + `docs/THEME_AUTHORING.zh.md`. Keep them in sync when the contract changes.
8. **Validate:** `npm test` (theme contract + import smoke + TypeScript check), then `npm run build`. The theme validator covers all builtin CSS skins, builtin JSON packs and the starter template: `:root[data-theme]` selectors, all contract tokens, declared background assets, and two-way `registry.ts` consistency. The import smoke test (`tests/theme-pack-smoke.mjs`) executes the real loader via esbuild.

### Adding a builtin theme (checklist)

- [ ] New `src/theme/themes/<id>.css` (or pack) filling every token
- [ ] `registry.ts` entry + id in `BUILTIN_THEME_IDS`
- [ ] i18n `theme.*` zh + en
- [ ] If art backdrop: place under pack folder; set `--bg-image` + opacity
- [ ] `npm test && npm run build`

### Forbidden

- Merging all themes into one giant `themes.css`
- Growing `tokens.css` with per-component shade ladders
- Theme-specific selectors against business class names
- Committing secrets, API keys, or local probe files (`.omo/`, `_me_write_probe.md`, ad-hoc `debug.sh` unless asked)

### Pet v1.2 liveliness layer (2026-11-10)

- The "alive" feel is **four independent transform layers, not more frames**: `.pet-figure` (facing + head gaze) → `.pet-weight` (center-of-mass sway + slow body gaze) → `.pet-motion` (breathing) → `.pet-secondary` (hair/head secondary motion) → `.pet-loops` (frame animation). Every layer is a pure transform container with **one WebP only** — duplicating an alpha WebP into two layers produces a double image.
- Idle cycles live only in `manifest.json` → `autoActions.liveliness.cycles` (`breathMs 3100` / `secondaryMs 5300` / `weightMs 7900`; coprime as 31/53/79 in 0.1s units) and are injected as CSS custom properties by `PetStage.tsx`. **Never hard-code animation periods in CSS**; `pet.css` only carries fallback values.
- Gaze uses three decreasing lerps from `autoActions.liveliness.gaze` (`eye 0.32 > head 0.13 > body 0.055`) writing `--gaze-x/y`, `--head-x/y`, `--body-x/y`. `usePetGaze` judges convergence on the **slowest** layer, otherwise head/body freeze early. The body layer uses the independent CSS `translate` property so it does not fight the animation's `transform`.
- ComfyUI scripts must call `comfyui_curl_http.install()` before any request: Python sockets to the LAN ComfyUI host are blocked (`Errno 65 No route to host`) while curl works. Trial scripts write **only to temp dirs**; no generated image may enter `src/assets/pet` before Qwen / LoRA licenses are closed.

### ComfyUI / Qwen-Image prompt engineering (2026-11-10, measured)

Four SCR-015 rounds / 12 images, same weights (`qwen_image_fp8_e4m3fn` + Lightning-8steps, 8 steps, cfg 1.0). These are measured findings, not guesses:

- **Long Chinese prompts lose tail instructions.** A ~900-char master prompt produced gradient backgrounds, knee-up framing, blue striped turtlenecks and halos on all three seeds. Keep master prompts short, hard constraints first.
- **"Full body" must name the lower body explicitly.** Writing only 全身 makes the fp8 model converge to knee-up framing. State trousers / two full calves / both shoes / gap between legs, plus English `full body head to toe, both legs fully drawn, both shoes visible, no cropping`. Same lesson is recorded in `comfyui_pet_assets.py` POSITIVE v2.
- **Any positive wording about 头顶 / Angel-ring / 发饰 induces a glowing halo.** Adding `halo` to the negative prompt does NOT suppress it; deleting the positive wording removes it entirely (v4). Never describe anything above the head in a master prompt.
- **Hard constraints compete for attention.** Putting only the white-background block first made all three images half-body (v3). Put both blocks first in English side by side (v4) → 3/3 full body, near-uniform white background, consistent styling across seeds.
- **Text-to-image is for the single master sheet only.** v4 proved three seeds can be stylistically consistent with a short prompt, but 28 different action prompts will still drift. Derive every expression/pose by image-to-image from the one locked master; never re-roll text-to-image per frame. The verified derivation chain is Qwen-Image-Edit 2509 + Multiple-angles LoRA (see the pose-derivation finding below), not the older v0.7 Edit chain.
- Trial outputs stay in temp dirs. Check the four-corner RGB spread before trusting any chroma key; a bbox close to the full canvas means the key failed (often a ground shadow), not that the character fills the frame. Ground shadows must be removed before a transparent overlay window.
- **Four-corner uniformity is NOT proof of a usable cutout** (2026-11-10, SCR-016, measured). `cel-20261112` passes the corner test (10/10/9) yet cannot be keyed: the character wears a white T-shirt / socks / shoes / rabbit charm, so a white-background chroma key punches holes in the clothing, while four-edge flood fill leaves an enclosed background wedge behind the hair plus a ground-shadow strip (8.07% residue). Re-rolling the same prompt with a magenta backdrop still produces a white floor and grey foot shadow (corner spread 18/146/58). **Any new master sheet must pass `check_pet_keyvisual_cutout.py` (five checks incl. residue ratio and white-garment retention) before it may seed asset production**; never promote a key visual on corner statistics alone.
- **Prefer a saturated pure-colour backdrop over white or magenta for any new master sheet** (2026-11-10, measured). A uniform cyan-blue `RGB(91,145,190)` sheet passes all five SCR-016 checks (residue 0.59%, white garments 100% kept, bbox 70.6%), because `min(G-R, B-G)` is strongly positive only for the backdrop and non-positive for black/grey/purple-red/mint character colours. Do **not** use connectivity flood fill on such sheets: large hair strands enclose background islands that flood fill cannot reach, leaving bright cyan blocks in the hair. Use the global `chroma` mode instead. White backdrops are the worst case because white T-shirts/socks/shoes share their colour.
- **The old "Qwen-Image-Edit cannot produce new poses" conclusion is superseded** (2026-11-10, measured). SCR-013/014 used the v0.7 Edit chain without the Multiple-angles LoRA. The installed ComfyUI 0.36.0 (RTX 5080 16GB, 2252 nodes) has `qwen_image_edit_2509_fp8_e4m3fn` + `Qwen-Image-Edit-2509-Lightning-4steps` + `Qwen-Edit-2509-Multiple-angles`; a locked-seed trial produced a 30-degree head turn and a raised-hand wave in 28.8s / 24.5s, with the character identity, outfit, framing and full-body shoes intact. Traditional `FrameInterpolationModelLoader` / `LoadBackgroundRemovalModel` / `WASRembgModelLoader` checkpoints are indeed still missing, **but they are no longer a blocker**: `minimax_h3_fl2va_pruned_int8_convrot` + `minimax_h3_fl2v_turbo_8step` + `qwen3vl_32b_minimax_h3_nvfp4_awq` + `minimax_h3_video_vae_fp16` + `SaveAnimatedWEBP` produced a 768x1152 / 22-frame / 24fps lossless video in 170.5s. All 22 frames pass SCR-016's five cutout checks and the 1000-frame budget is 5.27 MB. Keep the shipped 21-WebP / 100-frame v1.2 package as the single source of truth until the full replacement lands; **do not claim the 1000-frame action set is delivered**.
- **Both Edit 2509 and H3 drift the backdrop; never hard-code one background colour** (2026-11-10, measured). Edit 2509 moves the cyan-blue key from `(91,145,190)` to `(82,171,187)` (`min(G-R,B-G)` 47 -> 16); the old `detect_mode` requirement `B-G >= 20` misclassified that frame as a light backdrop and degenerated to a full-canvas bbox / 0.3% transparency. H3 drifts G from 142 to 170 across 22 frames. `check_pet_keyvisual_cutout.py` now uses `min(G-R,B-G) >= 8 && B-R >= 40` for detection and scales the chroma thresholds to **that frame's** background score. Per-frame four-corner sampling is mandatory in any batch pipeline.
- **Foot margin is a hard production gate, not a cosmetic note** (2026-11-10, SCR-018). The user master and every Edit/H3 derivative have 0px below the shoes, so any framing drift crops the sneakers. Pad the Edit input canvas with >= 2% empty backdrop below the feet before batch production; `check_pet_pose_series.py` rejects any pose or video frame failing this. A frame that looks good alone is not proof a sequence is producible — run SCR-018 on the whole pose set and the interpolated video first.
- **Padding the canvas alone creates a new defect: a glowing cyan platform under the feet** (2026-11-10, measured). Asking Edit 2509 to "keep a large empty margin below the shoes" made it paint a bright cyan ellipse (~`(90,230,245)`), 0.505% of the canvas. Its distance from the key colour exceeds `_CHROMA_NEAR=95`, so the chroma key's "protect saturated accessories" rule preserves it and all five SCR-016 checks still pass — a **false green**. The fix is prompt-level: state that the area below the shoes is the *same flat colour* as the rest of the backdrop and add `bright cyan ellipse / glowing platform / podium / spotlight circle / ground disc / light pool / turquoise circle / stage` to the negative prompt. Two locked seeds then scored 8/8 with 0.000% platform pixels and 11.6% foot margin. SCR-018 now has an explicit platform check so this regression cannot pass silently.
- **Licensing is CLOSED by the project owner (2026-11-10)** — the owner explicitly approved generating and bundling the locally produced action frames (original decision item 2). Deployment/redistribution is mainland China, which sits inside the MiniMax H3 Community License's permitted scope (it excludes on-prem use in US/EU/UK/Korea); Qwen-Image / Edit 2509 / Lightning / Multiple-angles / H3 LoRA weight licenses must still be recorded individually in `src/assets/pet/ASSETS.md`. Cloud ImageGen/VideoGen remain banned for in-package assets (cloud, no alpha, frame drift). Keep the license trace with every asset batch; re-check before shipping to any new region.
- **A cutout handed in from outside still needs its own gate** (2026-11-10, SCR-017, measured). `good.png` is the cleanest of three cutouts (0% cyan residue, 0 isolated specks, white garments 100% kept), yet 88.96% of its outline pixels are a 1–3px mint-green spill that SCR-016 cannot see because it only validates the keying step. Run `check_pet_cutout_asset.py --fix` before seeding any master: it replaces spill with inward neighbour colours, clears RGB garbage under alpha=0, and enforces the 1000-frame ≤8MB budget. The earlier user cutout and the AI global-chroma cutout both carry 31 isolated specks, and the latter also has a 10.33% cyan fringe; neither passes unmodified. **Never promote a cutout on "background residue is zero" alone.** A new character look must replace the whole 21-WebP package, not just the static poster — otherwise the old fog-blue short-hair frames and the new black-purple long-hair poster will be mixed in one loop.

### Pet v1.3 action registry / 1000 frames (2026-11-10)

- **`manifest.json` `poses[]` IS the action registry**: 20 actions × 50 unique bitmap frames = exactly 1000. Each entry declares `semantic`, `trigger`, `group`, `priority`, `states`, `motion`, `playback`, plus one exclusive poster and one exclusive loop. No cross-semantic reuse (drag must never reuse the walk pose). Adding an action = append one manifest entry + two WebP files + run `gen_pet_from_manifest.py`: `PET_ACTIONS` is generated sorted by descending priority, `PET_ACTION_TABLE` in `petState.ts` is a `map` over it, and `PetStage.tsx` resolves via `selectPetAction`. Frontend code must not change.
- **Priority strata are interaction > gateway state > fallback**: `lifted 100 / landing 99` > interaction and auto actions 80..47 > `typing 30 / error 29 / done 28 / sleep 27 / offline 26` > `idle 0`. If a state action outranks an interaction action, celebrate/disappointed/petted silently disappear. `trigger: always` marks a state action; every other trigger must equal its action name and is driven by a boolean flag.
- **Drag is three phases, not a boolean**: pointer-down → `lifted` (exclusive "picked up off the ground" frames + CSS lift and dangle), release with movement → `landing` (`autoActions.drag.holdMs`, exclusive landing frames), then `idle`. A pure click with no movement must NOT play landing. `usePetDrag` owns `dragPhase`; `PetStage` writes `data-drag-phase`; CSS never overlays a second figure.
- **Orientation is a hard production gate** (SCR-019): asking for "being lifted" made Edit 2509 flip the character 180° (hanging by the feet). The pipeline checks `white-shoes centroid − skin centroid > 0.08` on every key pose and every interpolated video's first frame; inverted frames are re-rolled once with a new seed, then rejected. Positive prompts must state `STILL UPRIGHT / head at top / feet at bottom`; negative prompts must list `upside down, inverted, hanging by the feet`.
- **Production chain**: `good.png` → SCR-017 fixed master → SCR-019 `comfyui_pet_action_series.py` (Qwen-Image-Edit 2509 key poses → MiniMax H3 FL2VA 56-frame interpolation → per-frame adaptive chroma key cached in `cutouts/` → **v1.3.2 union-safe-box + global target-height pure-scale normalization** → `180×297` source frames) → `pet_reencode_assets.py` (56-colour lossless; 96 and 64 colours both exceed the 8 MB budget). The blink extra frame must NOT be the same bitmap as the sleep poster: identical bytes get de-duplicated by the bundler's content hash and dist ships one file less (gate D04) → regenerate manifest/CSS/TS/preview → `npm test` / `npm run build` / `check_pet_overlay.py` (C36/C37, D06) + SCR-018 pose-series acceptance. Never swap only the poster: the whole 41-WebP set must be replaced together. The pipeline is resumable via `state.json` (`--phase keys|interpolate|frames|encode`).
- **v1.3 canvas was `160×297`, not `105×297`** (historical; v1.3.1 is `180×297`, see above): the new look has wide flowing hair, so the subject's aspect is ~0.56. Contain-fitting it into 105×297 (0.354) leaves the character at only 59% of the frame height. Also **never use a min/max union of per-frame alpha bboxes**: H3 edge noise pulls `getbbox()` to all four borders and the union becomes the whole canvas. SCR-019 uses a projection-threshold `tight_box` per frame. Keep `cropBox = [0,0,baseSize.w,baseSize.h]` and let `config.ts` read `PET_IMAGE_SIZE` from the generated constants instead of hard-coding a second value.
- **Generation canvas is `640×768` (v1.3.3), not `512×768`.** H3 interpolation pushes the subject toward the frame border; the 512 width permanently cut off fingertips (`wake` / `stretch` / `welcome`), hair tips (`landing` / `lookAround`) and shoe soles (`petted` / `wait`) in 15/20 measured videos. Offline normalization cannot recover pixels that never existed. Knobs: `SUGT_PET_CANVAS`, `SUGT_PET_MASTER_SCALE` (default `0.78`), `SUGT_PET_H3_STEPS=4`. SCR-019 `edge_touch_score` is a hard gate on every key pose and interpolated video (up to 3 seeds, otherwise reject and mark `state.json.rejected`); do not go below 640 wide or above 0.78 master scale without a new visual check.
- **Foot margin must be added at normalization, never assumed from the source video** (2026-11-10, full 20-segment SCR-018 run, measured). 13/20 H3 videos score 0–1.56% bottom margin: interpolation pushes the shoes onto the source canvas bottom, while the shared bbox lower edge is already clamped to `768`, so no extra backdrop exists below it. `do_frames()` therefore reserves transparent margin and applies the same scale/offset to every action **and** the blink extra frame — otherwise blinking shifts the figure. SCR-018 judges production input; SCR-020 `check_pet_final_frames.py` judges the 1000 shipped frames. Both layers are mandatory; a green SCR-018 alone never proves the package is fine, and a green SCR-020 does not erase a production-input deviation.

### Pet v1.3.1 — scale uniformity and safe margins (2026-11-10)

- **`baseSize` is `180×297`, not `160×297`** (the v1.3 value below is history). The v1.3 `160×297` frame has aspect 0.539 while the subject is ~0.58 wide: 18/20 actions had 0px left/right margin and `stretch` / `peek` / `wake` / `typing` push hands to `x=511` of the 512px source canvas. `180/297 = 0.606` is still narrower than the `.pet-figure` drawing area (~0.643), so `background-size: contain` stays **height-driven** and the character is not shrunk a second time. Widening past ~190 flips contain to width-driven and makes the pet smaller — do not do it without re-measuring.
- **Never normalize with a single global median bbox + fixed padding.** That aligns coordinates but not scale: Qwen-Edit / H3 drew each action at a different size, measured source-frame subject height 588–767px and shipped-frame height 215–275px (**27.9% spread** → visible "some pets tall, some short, some fat"). SCR-019 `do_frames()` now takes each action's 50-frame **per-edge median** as its representative box, normalizes every action's subject height to one `h_ref`, clamps per-action 90th-percentile excursion (25% width / 15% height) against H3 edge noise, then solves one shared `k` from the global worst-case width/height so every action fits with safe edges. All 50 frames of one action share the **same** crop box and scale (no intra-action jitter); all actions share one foot line and one horizontal centre (no jump on pose change). `do_frames()` self-checks `min four-edge margin ≥6px` and `cross-action height spread ≤8%` and raises before encoding.
- **Two safe-margin layers, both required.** Product CSS: `.pet-stage` defines `--pet-inset-x/y: 8px`, `.pet-figure` uses them on `top/right/bottom`, and `.pet-loop` / `.pet-poster` / `.pet-blink` use `background-position: center bottom` (center, not right, so `scaleX(face-x)` mirroring stays symmetric). The pet window keeps `overflow: hidden` — never change it to `visible` (transparent window has a hard physical clip and a rectangular halo would appear). Asset side: the normalization above reserves transparent margins on all four sides. `lifted` translates `-10px`, `pet-hop` `-7px`, `pet-poke` scales `1.03`; without both layers these clip hair/hands/shoes.
- **`figureHitRect()` must track the CSS alignment.** It now computes `originX = rect.left + (width - drawW) / 2` (center bottom), not `rect.right - drawW`. `figureRef` is bound to `.pet-figure`, so the inset is already inside `rect`. Updating `background-position` without this change shifts the click-through hitbox sideways.
- **SCR-020 gate additions**: per-action four-edge margin `≥6px` and cross-action subject-height spread `≤8%`, on top of the 1000-unique-bitmap / alpha / poster / blink / volume checks. A green old-style 83/83 is no longer sufficient evidence.

### Pet v1.3.2 — never crop the character, rebuild offline from the original videos (2026-11-10)

- **The original H3 videos are the only image source and are never lost.** `SUGT_PET_WORK/videos/*.webp` (20 × 56 frames, `512×768`) plus `keys/` and `su-master.png` remain on disk. `--phase frames` is **fully offline** (zero ComfyUI calls, zero credits): it re-keys the videos, then caches each of the 1000 RGBA frames as `cutouts/<action>/NNN.png`. Adjusting character size, margins or canvas is a cache-only rerun (minutes), NOT a regeneration. `--recut` forces a re-key; only a new character look / new action semantics needs `--phase keys|interpolate`.
- **v1.3 and v1.3.1 both CROPPED the character — that is the root cause of lost limbs.** v1.3 used a global median bbox + 20px pad; v1.3.1 used a per-action representative box ± 90th-percentile excursion clamped to 25%/15%. Any raised arm / foot outside those boxes was permanently removed from the shipped WebP. **Never reintroduce `frame.crop()` on character pixels in `do_frames()`.**
- **v1.3.2 normalization = pure scale + translate, no crop.** Per action take the **union** of the 50 robust `tight_box` results (the union by definition covers every limb of every frame); clear only chroma-key specks outside `union ± pad`. Solve ONE global target subject height `h_ref` as the minimum of 20 actions × 4 directional bounds (left/right/top/bottom), so `scale_i = h_ref / core_height_i` makes all 20 actions the same height. All 50 frames of one action share the same scale/offset; all actions share one foot line and one horizontal centre. `su-blink` uses the same function.
- **Three hard gates in `do_frames()`**: min four-edge margin `≥6px`, cross-action subject-height spread `≤8%`, and **solid pixels outside the union box `≤2%`** (a larger value means `tight_box` hid a real limb → abort before encoding). Measured on the 1000-frame rebuild: `h_ref=186.6px`, min margin `14px`, spread `1.6%`, hidden `0.000%`.
- **Size tradeoff is inherent, not a bug.** In the v1.3.2 source videos `greeting` hair reaches `y=0`, and `stretch` / `wake` arms reach `x=0` and `x=511` (already clipped by the generation canvas); `wake` was re-generated at 640×768 in v1.3.3 and is now complete. Fitting all of it into `180×297` with margins yields ~64% canvas height (old v1.3 measured 87% precisely because it cropped). Do not "fix" the smaller pet by widening the crop or pushing the canvas past ~190 wide (`contain` flips to width-driven and shrinks it further). To make the character larger, reduce `safe_x/safe_y` in `do_frames()` and rerun `--phase frames`; to enlarge on screen, use the existing `PET_SIZES` window presets.
- **Keep the acceptance layers distinct.** SCR-018 judges production videos, SCR-020 judges the 1000 shipped frames (four-edge margin, height spread, unique bitmaps), SCR-019 self-check judges "no limb cut". A green SCR-020 does not prove no limb was cut in normalization — `state.normalise.max_hidden` and the production trace are the evidence.

### Pet v1.3.3 — source-canvas clipping and roam semantics (2026-11-10)

- **Offline normalization cannot restore pixels missing from the source video.** v1.3.2 rebuilt all 1000 frames from the `512×768` H3 videos and proved `do_frames()` cut nothing — yet the user still saw "hands disappear when waking up". Measured: 15/20 source videos have real character pixels in the 2.5% border band (`wake`/`stretch` fingertips at `x=511`, `landing` flying hair at the right edge, `petted` shoes at the bottom). Those limbs were truncated by the generation canvas itself. Therefore `edge_touch_score` gates **production**, not packaging: `640×768` canvas + `SUGT_PET_MASTER_SCALE=0.78` + hard prompts (`BOTH HANDS COMPLETELY INSIDE THE FRAME`) + up to 3 seeds per key pose/video. Rejected actions are recorded in `state.json.rejected` and the rest of the batch continues; rerun only the rejected ones. **Delivered scope (2026-11-10): only `wake` was regenerated at 640×768 and shipped. The other 19 videos remain the v1.3.2 512×768 originals and are parked for later optimization — do not claim all 20 are clean.**
- **Re-generate only for missing source pixels.** Size / margin / canvas / hitBox adjustments still use the offline `--phase frames` + `cutouts/` cache path (minutes). Do not re-run ComfyUI for geometry problems, and do not try to "fix" a clipped hand by enlarging the window.
- **Roam = `lifted` → `landing`, never `walk`.** `petActionFlags()` maps `roaming` to `lifted` only when `state === 'idle'`: walking frames never align with window movement, and a `lifted` flag must not cover real `typing` / `error` feedback. `usePetBehaviors` sets `roamLanding` for one `AUTO.drag.holdMs` on arrival; `PetStage` adds `pet-landed`; CSS lifts the figure `-8px` with `pet-lift-float` / `pet-lift-dangle`. Drag keeps its own three-phase `dragPhase`. Gates C46/C46b/C46c/C46d/C47 assert the wiring.

## Backend / gateway

- Prefer existing Axum routes and config.toml hot-reload patterns.
- Codex takeover uses `model_providers.sugt` + `wire_api=responses` (see `codex_config.rs`).

### Codex Responses tool compatibility

A working Chat Completions bridge does **not** prove Responses compatibility. Keep the full tool loop working:

- `shell_command` is an official JSON-argument **function** tool. Never classify it as a freeform `custom` tool; classify by the request's tool declarations (`ChatToolMeta`), not by a hardcoded name list.
- Flatten `namespace` tools to `<namespace>__<name>` for Chat upstreams and restore the client name on the way back via `ChatToolMeta.flattened_names`.
- Never silently drop unknown `tools` (degrade schema-bearing ones to `function`, log the rest) and never stringify structured tool items (`mcp_call`, `*_output`, etc.) into user text. Pair orphan `tool_calls` with a `role=tool` result before sending upstream.
- Emit the complete SSE lifecycle: `response.in_progress`, `response.function_call_arguments.done` / `response.custom_tool_call_input.done`, `response.completed`, and a Responses-shaped `error` object on failure.
- **Degrade, never fake success.** An empty/invalid upstream body or a 4xx reply must produce a Responses-shaped `failed` response, not an empty `completed`. Fields the stateless gateway cannot forward (`previous_response_id`, `store`, `reasoning`, `include`, …) go into `ChatToolMeta.dropped_request_fields` with a warning instead of vanishing silently. Map `max_output_tokens` → `max_tokens`.
- **Streaming is hostile input.** Accumulate SSE bytes (not decoded strings) across chunks, never slice `&str` at a fixed byte offset, buffer `arguments` fragments until the tool name arrives so `output_item.added` always precedes `arguments.delta`, and give anonymous tool calls a resolvable fallback name at finalize time.
- `instructions` items in `input` become `system` messages; unknown items degrade to their plain text, never to a serialized JSON blob.
- Validate with `src-tauri/tests/codex_gateway_e2e.rs` (real HTTP + mock upstream, streaming and non-streaming) and `src-tauri/tests/codex_edge_cases.rs` (malformed/edge payloads). A passing text-only request is not sufficient.
- **Streaming and non-streaming error detection must share one predicate.** Use `is_real_error_value` for both `is_openai_compat_error_body` and `upstream_error_message`: a chunk carrying `error: null`, `""` or `{}` is a normal response, never a `response.failed`. Fixing only the non-streaming path silently breaks SSE event ordering.
- **Every `/v1/responses` failure exit must be Responses-shaped.** Wrap `proxy_responses_via_chat` errors at the `v1/responses` branch of `proxy_request` (non-streaming → `status: failed` JSON, streaming → `response.failed` SSE). Never let an exhausted attempt, 5xx or circuit breaker fall through to the generic `json_error(502)` handler.
- **Streaming proxy must not set a total request timeout** on the upstream HTTP client (a 600s wall clock previously mid-cut Codex tool loops). Use connect timeout + TCP keepalive only; short chat/probe helpers may use `build_upstream_client_with_timeout`.
- **Never strip `tools` proactively** (including experimental free channels). Match cc-switch / official gateway practice: convert Responses ↔ Chat while preserving tools; only enter command-mode after the upstream explicitly rejects function calling (`tools_unsupported_hint`), then retry once on the same attempt.
- **Store Codex/Claude one-click takeover** must call `install_clients_env` / `uninstall_clients_env` (writes env + `~/.codex/config.toml`). Template-page `apply_takeover_profile` is a separate path — do not substitute it in the Store panel.

## Agent adapters (single source of truth)

- All agent fingerprints, config capabilities and skill directory candidates live in `src-tauri/src/agent_adapters.rs`. Never hardcode `~/.claude/skills` etc. in a second module; derive from `by_id()` / `skill_dir_candidates()`.
- `ConfigCapability.writable_fields` describes what SUGT **actually writes**, not what a client officially supports. Do not claim config-file writes for clients that only use env vars.
- `preview_takeover` / `list_agent_capabilities` are read-only. Before applying a takeover, show the impact preview. SOUL gets the capability brief through `system_prompt` only — it must never write client config files itself.
- Codex config writes are backed up and snapshotted; `apply_codex_config` fails on invalid TOML instead of overwriting. Keep `clear_sugt_codex_overrides` byte-for-byte revertible.
- On takeover release, restore the three scalars SUGT unconditionally overwrites (`model`, `preferred_auth_method`, `cli_auth_credentials_store`) **from the snapshot**, never by matching their values: only touch a field whose current value equals what SUGT wrote, restore the pre-takeover value when present, delete only when it was absent. Users often had these fields before takeover; deleting them by value silently wipes their config. With no snapshot, leave the auth fields alone — residue is safer than data loss.
- `auth.json` is merged, not replaced: preserve existing ChatGPT login fields. Declare third-party capabilities (`requires_openai_auth`, `capabilities.remote_compaction`, `web_search`) so the client does not request hosted tools the gateway cannot serve.
- Codex `model` uses a `sugt-` alias so a same-named upstream model does not inherit the official `code_mode_only` / `use_responses_lite` tool protocol. Keep it switchable via `SUGT_CODEX_MODEL_ALIAS=off` and idempotent. Do **not** generate `model_catalog_json` from scratch — the published workaround exports the real catalog first, and a minimal hand-written catalog would replace the client's entire built-in model list.
- SUGT never writes or removes `mcp_servers`. `read_mcp_resource` / `list_mcp_resources` are client-side tools and only work when the client has its own MCP servers configured; say so in the preview and SOUL brief.
- **No snapshot does not mean "never clean".** v1.1.7 shipped without any snapshot mechanism and unconditionally overwrote `model`, `preferred_auth_method`, `cli_auth_credentials_store` and the whole `auth.json`. Detect that exact legacy shape (`model_provider=sugt` + unaliased `model` + provider without `requires_openai_auth`/`capabilities` + no injected `web_search` + no state file) and prune only the values SUGT is known to have written. For any other snapshot-less shape, keep the conservative "residue is safer than data loss" rule. `prune_sugt_auth_fields` must key off a deterministically-owned value (`auth_mode=apikey` plus a gateway key equal to the current one or `sugt-` prefixed) and preserve all other login fields.
- **`atomic_write` must never delete before replacing.** All platforms go through `replace_with_backup`: move the original to a pid-scoped backup, rename the temp file in, restore the backup on failure and clean the temp file. Windows `rename` cannot overwrite an existing target; the old "remove then rename" lost user config when rename failed.
- Regression suite for the release path lives in `src-tauri/tests/release_1_1_8_e2e.rs` (real HTTP gateway + mock upstream returning 4xx/5xx) alongside the existing Codex suites.
- **The agent catalog has one source, not two.** `agent_discover::known_agents()` derives the full client list from `agent_adapters::all()`; `fingerprints()` only holds legacy probe details (env var templates). An empty/short discovery query must return the whole known-client catalog, not `Vec::new()`. New domestic/global clients go into `ADAPTERS` only; clients with unconfirmed skill dirs use `GENERIC_CAPABILITY` and always include `~/.agents/skills` as fallback. Never claim a config-file write for them.
- **SOUL is a read-only orchestrator.** `soul_context::soul_brief()` injects runtime facts (capability matrix, taken-over clients, local skills, repos) into `system_prompt_with_brief()`. The model may only emit one `[[SUGT_ROUTE]]<intent>[[/SUGT_ROUTE]]` line (`clients` / `skills` / `preview` / `settings`), which the frontend renders as suggestion buttons. Never give SOUL a tool loop, never let it emit bash for management intents, never let it write client configs, clone repos or install skills. All writes go through the existing deterministic commands plus `TakeoverPreviewModal` impact preview and explicit user confirmation. Unknown/partial route tokens must be stripped, never executed or shown.
- **GitHub URL skill install is deterministic and transactional.** `store::github_install` reuses `parse_git_url` → host allowlist → `git clone --depth 1` (proxy-aware, `main`→`master` fallback) → `SKILL.md` scan → `replace_dir` → `staged.json`. It never registers a repo in `repos.toml`, caps the skill count, cleans the temp clone, and on failure restores `staged.json` and removes already-written dirs. It is idempotent (same URL overwrites the same ids). The frontend must guide users to Skills → Local Skills for mounting afterwards.
- **Trigger words and skill advice are rule-based, with LLM as optional explanation only.** `catalog::parse_skill_meta()` reads frontmatter (`triggers` / `触发词` / `when_to_use`, comma-separated or YAML list) and emits deterministic suggestions. Never invent trigger words from thin air; missing metadata produces an empty list plus an actionable suggestion. These still work when the model is unavailable.
- **Navigation:** Logs and About live under Settings as horizontal sub-tabs (`overview` / `general` / `appearance` / `advanced` / `pet` / `logs` / `about`), with `overview` first and `.settings-tabs` sticky. Desktop companion (小su) settings live on the `pet` tab between Advanced and Logs. The sub-tab state is owned by `App` so the status-bar drawer can jump straight to `logs`. High-frequency log polling is gated on the logs sub-tab being visible; the drawer keeps its own timer — do not double-poll.

## Release & packaging

- **Release asset names are stable and version-free.** Only the git tag carries a version. Builds always upload `SUTAI-windows-x64-setup.exe`, `SUTAI-windows-x64.zip`, `SUTAI-macos-arm64.zip`, `SUTAI-macos-x64.zip`, `SUTAI-linux-x64.tar.gz`, `SUTAI-linux-arm64.tar.gz` and `SUTAI-checksums.txt`. Never put a version in an asset filename again: the download site, the Homebrew cask and the in-app updater all resolve `/releases/latest` by filename, so a versioned filename forces a coordinated edit on every release.
- **Tags stay semantic (`v1.1.9`).** `update::check_for_update` compares `release.tag_name` with the bundled `CARGO_PKG_VERSION`; a fixed `latest` tag parses to `0.0.0` and silently disables update checks. Use `v*` tags, never a rolling tag.
- **One workflow, four build legs.** `.github/workflows/release.yml` runs on every `v*` tag push (and manual dispatch with an explicit tag): `windows-latest` builds NSIS + portable zip, `macos-15` / `macos-15-intel` build both macOS arches, `ubuntu-latest` / `ubuntu-24.04-arm` build **headless `sugt-cli`** tarballs (no Linux desktop GUI yet); a final `publish` job merges artifacts, writes checksums and uploads everything. CI never depends on the author-only `/scripts` PowerShell files (gitignored), and `package.json` `package:release*` entries remain local conveniences.
- **LAN / server mode is opt-in, auth-hardened.** Default bind stays `127.0.0.1`. `sugt-cli serve --lan` (or host `0.0.0.0` / `allow_lan_access`) binds non-loopback and **requires** a matching `gateway_client_api_key` on every request; missing headers are only tolerated on loopback for local Codex. Ship `deploy/sugt-gateway.service` as the systemd sample — do not make LAN the Linux platform default.
- **Homebrew is a rolling release.** `lsuen/homebrew-sugt` uses `version :latest` + `sha256 :no_check` + `releases/latest/download/<fixed-name>`; publishing a new SUGT version needs no tap change. Integrity is covered by `SUTAI-checksums.txt` and the GitHub asset `digest` used by the in-app updater. Users must run `brew upgrade --cask --greedy sugt` (or use in-app updates) because `:latest` casks are skipped by plain `brew upgrade`.
- **Download site reads `/releases/latest` too.** `lsuenweb` maps kinds to explicit asset names in `assets/projects.toml` and falls back to substring rules. Once names are stable, a new release only replaces same-named assets — neither repository needs a code or link change.
- **Version lives in six places**, not four: `package.json`, `package-lock.json` (two keys), `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json`, `src/release-notes.ts`. Run `python3 docs/孙测测/scripts/check_version_consistency.py --root .` before tagging.
- **Changing an asset name is a multi-place edit**: `release.yml` env, this section, both READMEs, the Homebrew cask (mac only), and `lsuenweb/assets/projects.toml`. Do it together or not at all.
- **Never declare platform-specific CLI binaries in devDependencies.** `@tauri-apps/cli` already installs the matching binary via optionalDependencies; pinning `@tauri-apps/cli-win32-x64-msvc` makes `npm ci` fail with `EBADPLATFORM` on macOS/Linux and kills the macOS release legs. Regenerate the lockfile with `npm install --package-lock-only` after any dependency edit.
- **Unit tests must be OS-neutral.** CI runs `cargo test` on `windows-latest`: build absolute paths from `std::env::temp_dir()` instead of `/tmp/...` literals, and cfg-gate POSIX-only shell commands (PowerShell's `pwd` prints a table, not a path).
