## 二、缺陷清单（10 字段紧凑格式）

### DEF-001 · 默认主密钥用量恒为「0次 0」（用户点名）

1. **问题**：默认入站主密钥被排除统计，用量永远为 0。
2. **触发条件**：默认安装，密钥池只有 `ensure_primary` 补种的 `sugt-local-key`，客户端带该 key 请求。
3. **预期结果**：请求的 `request_count` / `total_tokens` / 客户端明细如实累加。
4. **实际结果**：`gateway.rs:889-890` 对 DUMMY key 直接 `return None`，`note_client_key_use` 不记账；`list_client_keys` 返回全 0。**已确认**（代码链路 + 基线行为）。
5. **导致的现象**：接入 → 接入密钥长期显示「0 次 · 0」，用户以为功能坏了或数据在骗人；影响所有默认安装用户。
6. **根因**：`model.rs:544-546` 默认 key 是 `sugt-local-key`，`client_keys.rs:302-334` 用它补种 primary，但统计层把同一字符串当"占位符"排除。三处对同一 key 的身份认知不一致。
7. **修复后的结果**：池内 key（含默认主密钥）全部计入；无 header 请求仍不计（身份不可确定）。验收：`default_local_key_usage_is_recorded` E2E 断言 0→1、token 35、客户端明细 1 条。
8. **优先级 / 严重级别**：P1 / 一般 Major。
9. **状态**：已修复并复验。
10. **排除项**：前端写死已排除——`ClientKeyPanel.tsx:157` 走 `invoke('list_client_keys')`，`formatCount` 只做数字格式化；后端 `record_request` / `record_tokens` 本身正常。问题在统计入口的身份判断。

### DEF-002 · token 估算值冒充实测

1. **问题**：上游未返回 usage 时，把字符数估算写进用量统计。
2. **触发条件**：上游响应无 `usage` 字段（常见于兼容代理）。
3. **预期结果**：没有真实数据就不显示数字，估算只进日志。
4. **实际结果**：`gateway.rs:2881-2906`、`json_from_hold` 的 `parse_usage_from_bytes(...).unwrap_or_else(|| (estimate_input, estimate_output_tokens(...)))` 直接把估算写进 `record_tokens_attributed` / `record_key_tokens` / `record_client_tokens`；`gateway_stats.rs` 注释还声称存的是真实 usage。**已确认**。
5. **导致的现象**：配额告警、用量面板出现看似真实但不可信的 token 数；用户可能据此调整配额或判断成本。
6. **根因**：fallback 分支把估算值当作真实值返回，写入路径没有区分来源。
7. **修复后的结果**：无真实 usage → 0 写入统计，估算值只写 `estimated_input_tokens` / `estimated_output_tokens` 日志；注释更正。验收：`missing_upstream_usage_does_not_inflate_tokens` E2E 观察 1s，`total_tokens` 恒为 0。
8. **优先级 / 严重级别**：P1 / 一般 Major。
9. **状态**：已修复并复验。
10. **排除项**：流式路径 `tap_stream_for_token_stats` 只在 `parse_usage_from_bytes` 成功时统计，原本没有假数据；无需改。

### DEF-003 · 前端写死 model id `sutai`

1. **问题**：接入卡片与设置概览把公开 model id 写成品牌常量。
2. **触发条件**：公开 / 试用安装的 model id 与默认值不同，或用户改了别名。
3. **预期结果**：展示与复制都用后端下发的真实 `public_model_id`。
4. **实际结果**：`GatewayAccessBanner.tsx:96/123/147/162`、`SettingsOverview.tsx:30`、`AccessInfoCard.tsx:219`、`UpstreamSelector.tsx:130` 出现字面量。**已确认**。
5. **导致的现象**：用户复制到的接入信息与实际可用 model 不符，客户端配好却 404。
6. **根因**：前端用品牌名兜底，而不是把后端返回值当唯一来源。
7. **修复后的结果**：`GatewayAccessBanner` / `SettingsOverview` 用 `status.public_model_id`，无值显示空态且禁用复制；`AccessInfoCard` 用入口位置而非品牌名判断高亮；`UpstreamSelector` 保留 provider 已有别名，空串表示不改写。验收：`npm test` + `tsc` 通过；门禁 R2 零命中。
8. **优先级 / 严重级别**：P1 / 一般 Major。
9. **状态**：已修复并复验。
10. **排除项**：i18n 文案里的品牌名不算硬绑数据；`constants.ts` 的兜底 key 是配置读取失败时的展示兜底，已有注释说明不是可用密钥。

### DEF-004 · 占位 key `sugt-local-key` 多处重复定义

1. **问题**：同一业务常量在前端 / 后端多处写死。
2. **触发条件**：改默认 key 时漏改某处。
3. **预期结果**：单点定义，其它位置引用。
4. **实际结果**：`model.rs:545`、`clients.rs:7`、`bin/cli.rs:770`、`takeover_profiles.rs:315`、`GatewayAccessBanner.tsx:46`、`SettingsOverview.tsx:28` 均有字面量。**已确认**。
5. **导致的现象**：鉴权、客户端配置、接管脚本、UI 展示可能用了不同 key，排查困难。
6. **根因**：没有把 key 当配置契约常量管理。
7. **修复后的结果**：后端统一引用 `gateway_auth::DUMMY_LOCAL_KEY`，前端引用 `constants.ts::LOCAL_KEY_FALLBACK`。验收：门禁 R2 零命中。
8. **优先级 / 严重级别**：P2 / 轻微 Minor。
9. **状态**：已修复并复验。
10. **排除项**：测试夹具里的字符串不是生产数据，门禁按测试路径排除。

### DEF-006 · 网关日志无法串联一次请求

1. **问题**：入站、上游 key 选择、结果三段日志没有共同关联字段；skill 安装 / free 探测 / overlay IPC 失败静默。
2. **触发条件**：排障时需要还原一次请求的完整链路。
3. **预期结果**：一个 `request_id` 能 grep 出全链路，关键失败有日志。
4. **实际结果**：原 `gateway.rs` 日志只有 client/path/mode/latency；`note_key_attempt` 无日志字段；`logging.rs` 文件层未带 span；安装 / 探测 / IPC 失败无日志。**已确认**。
5. **导致的现象**：用户报「用量不对 / 请求失败」时只能靠猜，无法证实是哪一把 key、哪一步失败。
6. **根因**：日志缺少关联 ID 与结构化上下文。
7. **修复后的结果**：`InboundTarget` 带 `request_id`，贯穿入站日志、上游尝试、结果日志；入站 key 与上游 key 脱敏；文件层 JSON 带当前 span；skill 安装 / free 探测 / bind / overlay IPC 补 info/warn。验收：`json_file_layer_carries_current_span_fields` 单测 + `LogViewer` 白名单含 `request_id`。
8. **优先级 / 严重级别**：P1 / 一般 Major。
9. **状态**：已修复并复验。
10. **排除项**：耗时 `elapsed_ms` 原本已有，不重复加；日志不打印完整 key / token。

### DEF-009 · Responses 适配器合成的 usage 绕过统计侧过滤（DEF-002 的间接漏网路径）

1. **问题**：上一条缺陷只在网关直写路径堵住了估算值，但适配器层合成 usage 的路径仍会把估算写进统计。
2. **触发条件**：Codex / Responses 流式路径，且上游不返回 usage。
3. **预期结果**：估算值可给客户端做上下文预算，但不能进我们的用量统计。
4. **实际结果**：`openai_responses_adapter.rs:1481-1500` 的 `apply_usage_fallback` 用字符数兜底合成 `input_tokens` / `output_tokens`，并塞进发给客户端的 usage 对象；网关侧 tap 的是**转换后**的流，解析到的就是这个合成值，DEF-002 的「无 usage 不写统计」判断对它无效。**已确认**（代码链路 + 后端代理收尾时主动指出）。
5. **导致的现象**：走 Responses 协议且上游不回 usage 时，面板与密钥用量仍出现无法与实测区分的数字，与本轮修复目标冲突。
6. **根因**：估算与实测共用同一个 usage 字段，统计侧缺少判别依据。
7. **修复后的结果**：适配器合成 usage 时打 `sugt_estimated` 标记（`responses_usage` 增加 `estimated` 参数）；网关解析 usage 时读该标记，估算值只写 `debug` 日志、不进统计与 key 用量；上游实测 usage 不带标记，照常入统计。
8. **优先级 / 严重级别**：P1 / 一般 Major。
9. **状态**：已修复并复验（新增 2 个单测）。
10. **排除项**：客户端仍能拿到估算 usage——这是刻意保留的行为，因为 Codex 依赖 usage 做上下文预算，给 0 可能导致客户端误判；「假数据」问题只针对我们自己的用量展示与统计。

## 六、证据分级与排除项

**已确认**：所有缺陷均有文件:行号与代码链路支撑；门禁与脚本留痕在 `docs/孙测测/traces/`。

**待验证推断**：无。估算 token 的替代方案（分列展示估算值）本轮未做，因为需要新增前后端字段，超出本次修复范围；当前选择「不写统计、只写日志」。

**排除项**：
- 前端用量展示不是写死的——真实走 `list_client_keys`，已排除。
- 测试夹具里的 `mock` / `fake` 字符串不是生产假数据，门禁按测试路径排除。
- i18n 文案与单一真相源常量定义处的字面量不算硬绑。
- 流式 token tap 路径原本只统计真实 usage，无需修改。

## 七、遗留风险

1. 估算 token 现在完全不进统计，若上游持续不返回 usage，面板 token 会长期为 0。这是有意的「宁缺勿假」：需要成本分析时应让上游返回 usage，或后续单独提需求增加 `*_estimated` 分列展示。客户端侧仍会拿到估算 usage（Codex 依赖它做上下文预算），但那不进入我们的面板与统计。
2. 默认主密钥开始计数后，本机所有带该 key 的请求都会出现在用量里，数值会比以前大——这是真实值，不是回归。
3. `request_id` 是进程内短 ID（毫秒 + 原子计数），重启后会重置；跨进程 / 跨天追踪请用时间戳与日志文件名。

## 八、放行结论

**放行**。全量套件已跑完：Rust 492 通过 / 0 失败、前端 295 断言、构建成功、门禁 6/6 零命中、精灵两副本 85/85。无 P0、无数据丢失、无升级路径改动。遗留项为第七节三条（估算 token 不进统计、默认 key 用量变大、request_id 进程内），均已写明规避方式与后续排期方向，不构成本次阻断。

判定口径：P0 / 核心链路失败 / 数据丢失 / 升级路径不干净 / 全量套件未跑完 → 不能上线；仅 P2/P3 且有规避与排期才放行并写明遗留风险。
