## 二、缺陷清单（10 字段紧凑格式）

### WB-001 · 控制台切换模型会清空用户自定义模型别名

1. **问题**：`main.tsx` 传给 `GatewayAccessBanner` 的 provider 映射丢掉 `model_alias`，`UpstreamSelector` 保存时恒传空串，后端清空别名。
2. **触发条件**：用户设置过 `model_alias`（如 `my-model`），从控制台接入卡片的模型下拉切换模型。
3. **预期结果**：只改 `model_name`，对外 id 不变。
4. **实际结果**（已确认）：`src/main.tsx:936-947` 的 map 无 `model_alias`；`src/UpstreamSelector.tsx:388` 取 `provider.model_alias ?? ''`；`src-tauri/src/commands.rs:403-406` 把空串过滤成 `None`；`src-tauri/src/model.rs:96-103` 回落 `CLIENT_MODEL_ID`。后端 `ProviderView` 本就下发该字段（`model.rs:762`），前端类型 `main.tsx:251-268` 也未声明。
5. **导致的现象**：对外模型 id 静默变回 `sutai`，客户端配 `my-model` 的请求开始 404。
6. **根因**：报告 01 只修了 `UpstreamSelector` 写侧，没贯通 `main.tsx` 映射与类型。
7. **修复后的结果**：类型与映射补齐字段；验收：设别名 → 控制台切模型 → `list_providers` 的 alias/public id 不变，补前端映射字段完整性断言。
8. **优先级 / 严重级别**：P1 / 严重 Critical。
9. **状态**：已确认。
10. **排除项**：模型配置页内部的下拉不经过该 map，不受影响。

### WB-002 · 网关内部端点在 LAN 下无鉴权

1. **问题**：`/health`、`/v1/models`、`/v1/_sugt/traffic`、`/v1/_sugt/workspace-rules`、`/v1/_sugt/notify` 不校验入站 key，其中三个返回内部信息。
2. **触发条件**：用户开启 LAN 访问（`allow_lan_access`），同网段任意主机访问这些端点。
3. **预期结果**：LAN 下所有非健康检查端点都要匹配入站 key（AGENTS.md「LAN / non-loopback binds require a matching inbound key on every request」）。
4. **实际结果**（已确认）：`src-tauri/src/gateway.rs:813-829` 注册路由但只挂 CORS/Trace 层，无鉴权中间件；`841-856` 直接返回 traffic 统计与工作区规则注入全文；`957-975` 的 notify 只在请求**带了** key 且 key 无效时拒绝，不带 key 直接放行并 `note_client_key_use`。对比 `1130-1137`、`1172-1179` 的代理路由有显式校验。
5. **导致的现象**：局域网任何人可读取模型列表、请求量/客户端 IP、工作区规则内容，并可无鉴权投递 notify；信息泄露 + 统计被污染。
6. **根因**：鉴权写在各 handler 内而非路由层，新增内部端点时漏写；`notify` 的条件判断把「无 header」当成合法 loopback 场景，未区分来源 IP。
7. **修复后的结果**：统一路由层鉴权：loopback 可免 key，非 loopback 一律校验；内部端点按敏感度分级。验收：从非本机 IP 无 key 访问上述端点返回 401，带正确 key 可用。
8. **优先级 / 严重级别**：P1 / 严重 Critical（安全与隐私）。
9. **状态**：已确认。
10. **排除项**：`/health` 作为存活探针_public 合理，不是本条重点；代理主链路 `proxy_openai` / `proxy_anthropic_messages` 的校验正确。

### WB-003 · 程序化改主入站 key 不同步密钥池

1. **问题**：`update_gateway_settings.gateway_client_api_key` 只改 `AppConfig`，不更新 `client-keys.json` 中的 primary 记录。
2. **触发条件**：通过脚本/程序化调用该命令改主 key（接入信息卡、Codex 接管脚本走此路径），或在 UI 未走 `update_client_key` 的其它入口。
3. **预期结果**：改完主 key 后，`validate_client_request_with_keys` 使用的 enabled key 池同步生效。
4. **实际结果**（已确认）：`src-tauri/src/commands.rs:1640-1646` 仅 `config.gateway_client_api_key = trimmed` 并持久化；对比 `1425-1431` 的 UI 路径先改池内 primary 再同步配置。
5. **导致的现象**：接入卡显示新 key，客户端带新 key 请求被 401；旧 key 仍能用；用户按显示值配置却连不上。
6. **根因**：同一业务身份有两条写入路径，程序化路径绕过密钥池。
7. **修复后的结果**：该命令内复用与 `update_client_key` primary 分支相同的同步逻辑（改池 + 改配置 + 一次持久化）。验收：E2E 调 `update_gateway_settings` 改 key 后，用新 key 请求成功、旧 key 失败。
8. **优先级 / 严重级别**：P1 / 严重 Critical（认证失效）。
9. **状态**：已确认。
10. **排除项**：UI 的 `ClientKeyPanel` 路径正确同步，不是所有改 key 入口都坏。

### WB-004 · 防假数据门禁 R6 是空规则（假绿）

1. **问题**：R6 只在 `DUMMY_LOCAL_KEY` 所在行的后 3 行内找 `return None`，且 `iter_code_lines` 会剔除注释行；当前代码把排除逻辑改成 `allowed.iter().any(...)`，注释滚动后任意位置的直接排除都不会命中。
2. **触发条件**：未来任何人在 `inbound_target` 或别处重新加回「默认主 key 不计数」的排除，或把同样逻辑挪到其它函数。
3. **预期结果**：R6 能拦住「默认主密钥被排除统计」这一类回退。
4. **实际结果**（已确认）：`docs/孙测测/scripts/check_no_fake_data.py:384-407` 的窗口判断；`159-165` 的 `iter_code_lines` 剔除注释/测试块；当前 `gateway.rs:910-920` 的 DUMMY 附近全是注释，`code_lines` 中该行后继窗口无 `return None`，规则永远为 0 命中。本轮实跑 R6 输出「0 项命中」但代码根本没有该分支。
5. **导致的现象**：门禁显示通过，实际不保护 DEF-001 的修复；报告 01 的「6/6 零命中」给人虚假安全感。
6. **根因**：规则实现绑定了某个具体代码形状，而不是检查语义（默认 key 是否计入统计）。
7. **修复后的结果**：改为检测「默认 key 常量出现在统计入口的排除条件中」或直接用 `client_keys_e2e` 的 `default_local_key_usage_is_recorded` 作为门禁；验收：人为在 `inbound_target` 加回 `if presented == DUMMY_LOCAL_KEY { return None }`，R6 必须报失败。
8. **优先级 / 严重级别**：P1 / 严重 Critical（测试基建失效）。
9. **状态**：已确认。
10. **排除项**：R1~R5 确有实际扫描逻辑，不是全部无效；本条只针对 R6。

### WB-008 · 鉴权拒绝请求以 0ms 计入平均耗时

1. **问题**：`record_inbound_denied` 把拒绝请求以 `latency_ms = 0` 写入请求统计，拉低「平均耗时」。
2. **触发条件**：LAN 暴露后大量无效 key 请求，或本机频繁用错 key。
3. **预期结果**：拒绝可计失败数，但不贡献虚构的 0ms 耗时样本。
4. **实际结果**（已确认）：`src-tauri/src/gateway.rs:668-669` 调 `record_failure_stats(0, ...)`；`src-tauri/src/gateway_stats.rs:186-187` 无条件累加 latency 与 count；`src/TrafficPanel.tsx:194` 展示 `avg_latency_ms`。
5. **导致的现象**：平均耗时随拒绝数下降，看似网关更快，实则统计口径错误，违反「展示数字必须来自真实来源」。
6. **根因**：拒绝路径复用会累加耗时的统计函数，没有「无耗时样本」的表达方式。
7. **修复后的结果**：拒绝只计失败数，不加 latency 样本；验收：1 条 100ms 正常请求 + 5 条拒绝，平均仍 100ms。
8. **优先级 / 严重级别**：P2 / 一般 Major（数据真实性）。
9. **状态**：已确认。
10. **排除项**：正常失败（`record_proxy_hit`）有真实耗时，不在本条范围。

### WB-009 · mask_secret 对非 ASCII 密钥会 panic

1. **问题**：`mask_secret` 用字节下标切字符串，`secret.len()` 是字节数，非 ASCII 会切在 UTF-8 字符中间。
2. **触发条件**：用户把入站 key 或上游 key 设成含中文/emoji 的字符串，随后网关记录日志。
3. **预期结果**：任意用户可输入字符串都能安全脱敏，不崩进程。
4. **实际结果**（已确认）：`src-tauri/src/model.rs:898-903`：`if secret.len() <= 8` 后 `&secret[..4]` / `&secret[len-4..]`；8 字节以上的中文串必然触发 `byte index is not a char boundary` panic。该调用已进入热路径：`gateway.rs:896`（每次入站命中）和 `3879`（每次上游 key 尝试）。现有测试只覆盖 ASCII key。
5. **导致的现象**：一次带非 ASCII key 的请求就能让网关任务 panic；轻则日志缺失，重则请求失败/服务中断。
6. **根因**：UTF-8 字节与字符边界混用，新增日志调用放大了原有函数的影响面。
7. **修复后的结果**：改用 `secret.chars()` 计数与切片，或 `get(..4)` 安全回退；验收：中文/emoji key 的脱敏单测通过且网关请求不 panic。
8. **优先级 / 严重级别**：P2 / 一般 Major（稳定性）。
9. **状态**：已确认。
10. **排除项**：ASCII key 的行为正确；`mask_secret` 不是鉴权函数，不影响 key 匹配。

### WB-010 · 原生 Responses 路径的嵌套 usage 不入统计

1. **问题**：`extract_usage_from_json` 只读响应对象**顶层** `usage`，原生 Responses 事件把 usage 放在嵌套对象里，解析必然 None。
2. **触发条件**：上游原生支持 `/v1/responses` 且返回 usage（非经 chat 适配），走 `gateway.rs:2345-2354` 的直通分支。
3. **预期结果**：上游实测 usage 计入统计。
4. **实际结果**（已确认）：`src-tauri/src/gateway.rs:2345-2354` 直通 `into_axum_response`，其内部 `tap_stream_for_token_stats` 用 `parse_usage_from_bytes`；`4169-4190` 的 `extract_usage_from_json` 只 `value.get("usage")`，不递归查找 SSE 事件内的 `response.usage`。无 usage 分支按设计记 0。
5. **导致的现象**：原生 Responses 路径的 token 用量长期为 0，即使上游如实返回；用户误以为统计坏了。
6. **根因**：usage 提取器假设 OpenAI Chat 的顶层结构，没覆盖 Responses 的事件结构。
7. **修复后的结果**：提取器支持顶层与 `response.usage`/嵌套 usage，并保留 `sugt_estimated` 判别；验收：给原生 Responses SSE 注入真实 usage，统计 total_tokens 如实增加。
8. **优先级 / 严重级别**：P2 / 一般 Major。
9. **状态**：已确认。
10. **排除项**：Codex 经 chat→responses 适配的路径有单测覆盖，不在本条范围。

### WB-012 · R5 位深度比较未使用权威常量

1. **问题**：R5 定义了 `DEEPSEEK_DOC_URL_AUTHORITATIVE` 却只用在留痕文案里，判定逻辑只做前后端两两比较。

5. **导致的现象**：两端可以一起漂移且门禁仍绿，权威常量成为摆设。

9. **状态**：已确认。
10. **排除项**：当前两端值确实一致，不是现存数据漂移。

### WB-013 · R3 估算 token 规则按整个文件豁免

1. **问题**：文件级 `has_flag` 只要出现任意 `estimated` 字样，就跳过该文件所有 token 写入检查。
2. **触发条件**：同一文件既有合规的估算标记，又新写一处无标记的估算值写入。

4. **实际结果**（已确认）：`docs/孙测测/scripts/check_no_fake_data.py:266-278`：`has_flag = any(ESTIMATED_FLAG_PATTERN.search(line) for _, line in code_lines)`，随后 `if ... or has_flag: continue`。`gateway.rs` 本轮新增多处 `estimated_*` 日志，导致整个文件的 R3 检查被关闭。

8. **优先级 / 严重级别**：P2 / 一般 Major（测试有效性）。
9. **状态**：已确认。
10. **排除项**：R3 的 `TOKEN_WRITE_PATTERN` 本身能识别写入点，问题只在豁免逻辑。

### WB-015 · 设置概览空 model id 的复制按钮未禁用
