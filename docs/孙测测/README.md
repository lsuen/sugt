## 二、命名规范（配置管理）

| 对象 | 规则 | 1.1.8 示例 |
| --- | --- | --- |
| 报告目录 | `reports/sugt<主>-<次>-<修>上线评估/` | `reports/sugt1-1-8上线评估/` |
| 报告文件 | `sugt<主>-<次>-<修>测试报告NN.md`，NN 从 01 递增 | `sugt1-1-8测试报告01.md` |
| 留痕文件 | `<检查项>-<YYYYMMDD-HHMMSS>.md` | `版本一致性检查-20261106-195900.md` |
| 脚本文件 | 小写蛇形、动词开头、`.py` | `check_version_consistency.py` |

**编号语义**：`01` = 上线前首轮评估测试；`02` = 开发修复后的**缺陷复验 + 上线前回归测试**；`03+` = 再次修复后的追加轮次。报告只增不改，历史结论永久留痕。

> ⚠️ **待确认项（编号 CFG-001）**：本次指令中版本写为 `1.1.8`，但示例文件名为 `sugt1-8-8测试报告01.md`，两者不一致。按配置管理可追溯原则，**本目录默认采用与版本语义一致的 `sugt1-1-8`**；若确认要按字面 `sugt1-8-8` 执行，一句话告知即可批量改名。该点在确认前不得作为「已确认」结论写入正式报告。

## 三、脚本编写规范（测开产出）

1. **文件头必须声明**：脚本名称、**编写人员：孙测测**、作用用途、适用项目、创建日期、复用方式、退出码约定。
2. **注释与文档字符串一律中文**，关键分支要有「为什么这么判」的说明，不写 obvious 注释。
3. **遵循 PEP8**：4 空格缩进、行宽 ≤ 88、小写蛇形命名、import 分组（标准库 / 第三方 / 本地）、类型注解、模块级 docstring。
4. **标准库优先**，不引入无必要的第三方依赖，降低跨环境复用成本。
5. **参数化**：路径、期望值、输出位置一律走 `--root` / `--expect` / `--out` 等参数，禁止硬编码本机绝对路径与常量。
6. **必须留痕**：每次执行输出结构化 Markdown 到 `traces/`，含执行时间、输入参数、逐项结果、结论、复核命令。
7. **退出码语义固定**：`0` 通过 / `1` 检查不通过 / `2` 读取或解析失败，便于 CI 与批量编排。
8. **可复用优先**：把「可判定的检查」交给脚本（版本一致性、契约字段、测试汇总解析、日志统计），LLM 只承担需要判断与设计用例的部分——**减少重复读取与重复推理的开销**。

## 四、两套测试策略（成本取向不同）

| 场景 | 取向 | 做法 |
| --- | --- | --- |
| 日常迭代 / 常规检查 | **降本、复用** | 优先调用 `scripts/` 既有脚本 + `npm test` / `cargo test` 既有链路，结果落盘留痕；检查类任务默认只报告、不改代码 |
| **上线前评估测试** | **不计成本、最稳妥** | 按上线标准全量执行：功能 / 业务 / 前端 UI / 白盒架构 / 性能 / 兼容 / 安全、既有全量测试套件、真机构建产物、升级与回滚路径、遗留态构造；不因耗时而降级，不用「抽样」替代全量 |

## 五、上线闭环工作流程（标准软件工程流程）

1. **接收上线评估**：确认被测版本、构建号、目标平台、环境、范围；用 SCR-001 核对 6 个文件 / 7 个版本键一致（脚本）。
2. **首轮评估测试**：按第四节「上线标准」全量执行，出 `sugt<版本>测试报告01.md`，含 CMMI3 汇总层（通过率、缺陷分布、遗留风险、**放行结论**）。
3. **不通过则拦截**：存在影响上线的缺陷 → 报告必须给出明确 **「不能上线」** 结论，列出阻断项与证据，经 `handoff/HANDOFF.md` 对接给开发。
4. **开发修复后不重头乱测**：我按用户指令重点做两件事 ——
   - **① 首轮缺陷复验**：逐条按原复现步骤验证，确认「已修复 / 未修复 / 引入新问题」，每条带前后证据对比；
   - **② 上线前回归测试**：覆盖受影响模块 + 关联链路 + 全量既有套件，确认无回归。
5. **出 `测试报告02.md`**：给出复验结论、回归结论、残留风险、**最终放行 / 继续拦截**结论。
6. **仍未通过** → 回到第 3 步，编号 `03` 递增，绝不跳过复验直接放行。
7. **放行** → 报告 + 留痕 + 对接单一起归档，版本号与构建号可双向追溯。

## 六、报告最小字段（CMMI3 以上）

- **报告头**：报告编号与标题、被测版本 / 构建号 / 目标平台 / 测试环境、测试范围、执行时间、执行人（孙测测）。
- **单条缺陷（10 条固定字段）**：缺陷 ID + 标题 → 复现步骤 / 触发条件 → 预期结果 → 实际结果（带文件:行号 / 命令输出 / 日志片段）→ 导致的现象与影响范围 → 根因（未定位写「根因待查」，不许猜）→ 修复后结果与验收方式 → 问题类型（功能 / 业务 / UI / 架构 / 性能 / 兼容 / 安全等）→ 问题定位（模块·文件:行号）→ 优先级 P0–P3 → 严重级别 Blocker / Critical / Major / Minor → 状态。
- **汇总层**：用例统计与通过率、缺陷分布、遗留风险、修复建议、回归与验收策略、**放行结论**、证据与附件清单。
- **铁律**：先说问题→现象→修完会怎样，再谈背景；「已确认」与「待验证推断」分开列；必须给「排除项」说明为何不成立；中文输出；执行（尤其 Git）前先报告并确认。

## 七、与项目既有目录的关系

- **本目录**：孙测测的可复用 Python 脚本、留痕、对接文档、版本测试报告（人工/脚本混合评估产物）。
- **项目 `tests/`**：产品级自动化测试（如 `theme-pack-smoke.mjs`）仍留在原处，保持 `npm test` 链路不变，不搬迁、不重复造轮子。
- **项目 `src-tauri/tests/`**：Rust 单元 / e2e 测试保持原状，脚本只负责**调度与汇总**，不复制断言逻辑。
- **项目 `docs/小精灵维护/`**（2026-11-10 新增）：面向后续维护者的自包含手册目录（v1.3 定版脚本**只读副本**、`manifest.json` 快照、master 基准图、动作接触图、素材清单、动作表、更新维护手册、脚本说明手册）。其 `scripts/petctl.py` 登记为 **SCR-021**，可统一调度本目录定版脚本并做副本一致性自检；**脚本编辑源仍是本目录 `scripts/`**，副本由 `sync` 单向同步，避免双份真相源漂移。留痕与报告仍只写本目录 `traces/` / `reports/`。
