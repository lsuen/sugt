## 一、结论先行

**本轮判定：不能作为「交互已完成」版本放行。** 共发现 11 项缺陷，其中 P0 一项（流式在途状态失真）、P1 五项（编辑态不可用、拖动状态机误判、动画僵住、气泡遮脸）、P2 四项、P3 一项。核心现象是：**长流式请求期间精灵提前停止「处理中」并提前报「已完成」，用户感知为「状态乱跳 / 有 bug」**；另有编辑态控件点不到、拖动后误触主窗口等问题。

## 二、缺陷清单（10 字段紧凑格式 · 均为「已确认」）

### PET-001　流式请求期间在途计数提前归零，状态与成功播报双双失真
- **复现/触发**：网关开启 → Codex 发起一次 SSE 流式对话（响应持续 > 2s）→ 观察精灵。
- **预期**：整个响应体输出期间保持 `typing`，流结束后才出现结果级气泡。
- **实际（已确认）**：`let _active_guard = state.begin_request()` 在 handler 内创建，`proxy_openai` / `proxy_anthropic_messages` 返回 `Response<Body>` 时即被 Drop（`src-tauri/src/gateway.rs:658`、`691`），而 SSE body 由 hyper 在 handler 返回后继续发送；`traffic_stats()` 读取的 `active_requests`（`gateway.rs:199`）因此在响应头到达时就变 0。前端仅靠 `typingUntil = now + 1500` 的余晖（`src/overlay.tsx:197`）掩盖，长流超过 1.5s 即回落 `idle`/`done`。同时 `record_proxy_hit → record_request_stats`（`gateway.rs:305`、`865-877`）在上游响应头到达时就给 `success_count` +1，前端 `doneBatch` 静默 8s 后弹出「完成 N 次请求」（`overlay.tsx:184-195`），**流还在输出就已报完成**。
- **现象/影响**：所有使用流式输出的客户端（Codex / Claude Code / OpenAI 兼容）长时间生成时，精灵显示「待机中」或提前报成功；属于「不虚报状态」红线的直接违背。
- **根因**：在途计数的生命周期绑在 handler 栈帧上，未绑在响应体生命周期上；成功计数的记录点早于流结束。
- **修复后结果/验收**：守卫随响应体结束（或客户端断开）才释放；成功气泡在 `active_requests == 0` 后才开始合并计时。验收：构造流式 body 单测，断言「流未结束 active=1 / 结束后 active=0」；`cargo test` 全绿；检查 `overlay.tsx` 的 done 合并逻辑带 active 判断。
- **类型**：功能 / 业务状态一致性　**定位**：`gateway.rs:658,691,199`、`overlay.tsx:184-197`
- **优先级 P0　严重级别 Blocker　状态**：待修复

### PET-002　精灵编辑态「保存」与拖动把手不可点击
- **复现/触发**：开启精灵 → 开启编辑态（`cfg.edit = true`）→ 点击右上角保存按钮或拖柄。
- **预期**：按钮/拖柄响应点击与拖动。
- **实际（已确认）**：`.pet-stage { pointer-events: none }`（`src/overlay.css:164`），仅 `.pet-stage.interactive .pet-frame { pointer-events: auto }`（`:168`）；`.pet-edit-bar`（`:305-313`）及其内部 `.overlay-save` / `.overlay-grip` 未重新开启，继承 `none`。窗口虽已解除原生穿透，CSS 层仍吃掉事件。
- **现象/影响**：精灵模式下「编辑位置 → 保存」链路完全失效，用户只能去设置页点「回到右下角」。
- **根因**：pointer-events 继承未在新容器上显式覆盖。
- **修复后结果/验收**：`.pet-stage.interactive .pet-edit-bar { pointer-events: auto }`；浏览器命中测试可见按钮，保存后位置写盘。
- **类型**：UI / 功能　**定位**：`overlay.css:164,168,305`、`overlay.tsx:224-235`
- **优先级 P1　严重级别 Critical　状态**：待修复

### PET-003　任何窗口移动都会触发拖动收尾，污染单击判定并产生无谓写盘
- **复现/触发**：启动应用（恢复窗口位置）／切换精灵尺寸／点「回到右下角」／吸附自身触发的二次移动。
- **预期**：只有用户真正拖动才执行吸附 + 持久化。
- **实际（已确认）**：`getCurrentWindow().onMoved` 回调不区分移动来源，一律 `draggedAt.current = Date.now()` 并在 320ms 防抖后调用 `pet_finish_drag`（`overlay.tsx:106-131`）；后端该命令会 `runtime.persist()` 写盘（`commands.rs:1336-1350`）。
- **现象/影响**：启动/改设置后 700ms 内单击精灵被吞（`overlay.tsx:252`）；无意义的配置写入与潜在 `set_position → onMoved` 回环。
- **根因**：缺少「拖动进行中」状态位，把系统/后端发起的移动当成用户拖动。
- **修复后结果/验收**：只有 `mousedown → onMoved` 序列才收尾；启动与设置改动的移动不写盘、不污染 `draggedAt`。
- **类型**：交互 / 架构　**定位**：`overlay.tsx:106-131,252`
- **优先级 P1　严重级别 Major　状态**：待修复

### PET-004　拖动后停顿再松手会误触发「单击回主窗口」
- **复现/触发**：按住精灵拖动 → 停在目标位置不动超过 700ms → 松手。
- **预期**：仅保存位置，不弹主窗口。
- **实际（已确认）**：互斥只靠 `Date.now() - draggedAt.current < 700`（`overlay.tsx:252`），而 `draggedAt` 只在 `onMoved` 时更新（`:112`）；停顿时不再更新，松手产生的 `click` 越过 700ms 窗口。
- **现象/影响**：每次「慢慢拖、停一下再松手」都会把主窗口抢到前台，干扰当前工作。
- **根因**：用「最后一次移动时间戳」代替「本次按下是否发生过移动」。
- **修复后结果/验收**：以 `movedDuringDrag` 布尔位为主判据，配合 pointerup/超时清理；拖动后松手的 click 必被吞，纯单击仍可回主窗口。
- **类型**：交互　**定位**：`overlay.tsx:100-102,112,250-254`
- **优先级 P1　严重级别 Major　状态**：待修复

### PET-005　done/error 状态动画覆盖呼吸动画，角色在保持期内僵住
- **复现/触发**：完成一次请求或触发一次失败 → 观察 3.5s / 6s 保持期。
- **预期**：结果动效播完后继续呼吸。
- **实际（已确认）**：`.pet-frame` 基础样式为 `animation: pet-breathe ... infinite`（`overlay.css:188`），状态规则用同名 `animation` 覆盖为 `pet-done 0.6s 1` / `pet-error 0.4s 2`（`:201-202`）；一次性动画结束后元素不再有动画。
- **现象/影响**：完成/出错后角色完全静止数秒，像卡死，与「持续活着」的桌面宠物预期相反。
- **根因**：呼吸与状态动效争抢同一元素的 `animation` 属性。
- **修复后结果/验收**：外层承载呼吸、内层承载状态动效，两者独立；done/error 动画结束后呼吸不中断。
- **类型**：UI / 动画　**定位**：`overlay.css:178-209`
- **优先级 P1　严重级别 Major　状态**：待修复

### PET-006　气泡与悬停浮层盖住角色头部，字号过小且无法外扩
- **复现/触发**：触发任意结果级事件（网关就绪 / 请求失败 / 批量完成）。
- **预期**：气泡可读且不遮挡立绘。
- **实际（已确认）**：`.pet-stage { overflow: hidden }`（`overlay.css:163`）把气泡锁在 120×160 窗口内，气泡 `top:2px; left:2px; right:2px; font-size:9px`（`:253-268`）；素材实测 360×560（`sips` 输出），`background-size:contain + center bottom`（`:184-186`）后角色头顶贴近窗口 y=0，气泡三行文字正好压在脸上。`.pet-hover` 同样占顶部区域（`:266-270`）。
- **现象/影响**：小尺寸默认档下通知基本不可读，且遮住角色最关键的面部。
- **根因**：窗口尺寸未给通知留白，通知与立绘共享同一矩形。
- **修复后结果/验收**：窗口左侧增设通知栏（立绘靠右、大小不变），气泡字号 ≥10px 且不覆盖立绘；移除重复 hover 浮层。
- **类型**：UI　**定位**：`overlay.css:163,178-186,251-284`、`overlay.tsx:261-270`
- **优先级 P1　严重级别 Major　状态**：待修复

### PET-007　状态指示重复渲染
- **复现/触发**：精灵常驻时观察。
- **预期**：一处清晰的状态表达。
- **实际（已确认）**：`.pet-core` 右下角六边形状态灯（`overlay.css:237-249`、`overlay.tsx:258`）与 `.pet-status-bar` 左下角六边形 + 文字（`overlay.css:286-303`、`overlay.tsx:272-275`）同时表达同一 `petState`；`.pet-hover` 再重复一次文字。
- **现象/影响**：120×160 内三处状态元素，视觉杂乱、挤占立绘空间。
- **根因**：v0.3→v0.5 迭代中状态灯与状态条叠加，未做收敛。
- **修复后结果/验收**：合并为单一状态胶囊（灯 + 文字），移除独立 core 与 hover 浮层。
- **类型**：UI　**定位**：`overlay.css:237-303`、`overlay.tsx:258,266-275`
- **优先级 P2　严重级别 Major　状态**：待修复

### PET-008　贴边吸附按窗口左上角选显示器，跨屏时吸到错误屏幕
- **复现/触发**：双屏环境，把精灵从主屏拖到副屏且窗口左上角仍落在主屏。
- **预期**：按窗口实际所在屏幕吸附。
- **实际（已确认）**：`snap_position` 用 `point_inside(x, y, ...)` 找显示器（`overlay.rs:128-135`），`x/y` 为窗口左上角。
- **现象/影响**：跨屏拖动后精灵被拽回另一块屏幕边缘。
- **根因**：显示器归属判定取点错误。
- **修复后结果/验收**：改用窗口中心点判定；新增纯函数单测覆盖跨屏场景。
- **类型**：兼容 / 多显示器　**定位**：`overlay.rs:112-170`
- **优先级 P2　严重级别 Major　状态**：待修复

### PET-009　越界回位只校验左上角，拔屏后窗口可大部分不可见
- **复现/触发**：保存一个靠近右下角的位置 → 拔掉副屏或降低分辨率 → 重启。
- **预期**：窗口整体不在任何屏幕内时重新停靠。
- **实际（已确认）**：`ensure_on_screen` 只用 `point_inside(cfg.x, cfg.y, ...)`（`overlay.rs:87-103`），只要左上角落在某个屏幕内就认为合法，不检查窗口右下角。
- **现象/影响**：精灵大部分越出屏幕，只剩一角可见，且不自动回位。
- **根因**：可见性判定只取单点，未考虑窗口尺寸。
- **修复后结果/验收**：按「窗口完整落在某显示器内」判定（物理像素 + scale），否则重定位；补单测。
- **类型**：兼容 / 位置恢复　**定位**：`overlay.rs:78-108`
- **优先级 P2　严重级别 Major　状态**：待修复

### PET-010　尺寸档位被重置、设置写入存在覆盖竞态
- **复现/触发**：选「大」→ 关闭再开启精灵；或 3s 内连续点「中」「大」。
- **预期**：保留上次尺寸；连续操作按最后一次生效。
- **实际（已确认）**：`togglePet` 开启时无条件写 `PET_SIZES[0]`（`SettingsPanel.tsx:225-237`）；`setOverlay` 以父组件 3s 轮询的 `config.overlay` 为 base（`:218-220`），快速连点会用同一份旧 base 各算各的，后完成的写覆盖先完成的。
- **现象/影响**：用户尺寸偏好丢失；设置项开关偶发「点了没生效」。
- **根因**：本地草稿与父级轮询状态未解耦。
- **修复后结果/验收**：开启时保留已选档位；本地 `overlayRef` 累积最新配置，连续写入不回退。
- **类型**：功能 / 交互　**定位**：`SettingsPanel.tsx:218-245`
- **优先级 P2　严重级别 Major　状态**：待修复

### PET-011　文案与实现口径不一致 / 过时注释
- **复现/触发**：阅读设置页「拖动后贴边吸附」说明与后端校验注释。
- **预期**：文案描述实际行为。
- **实际（已确认）**：`set.petSnapHint` 写「松手时自动停靠到最近的屏幕边缘」（`i18n.ts:296`、英文 `:1161`），实现仅在离边缘 32 逻辑点内才吸附（`overlay.rs:140-163`）；`set_overlay_config` 注释仍称「精灵模式需要 240x320」（`commands.rs:1481`），当前默认 120×160。
- **现象/影响**：用户对吸附行为的预期被抬高，误以为放屏幕中间也会被拽走。
- **根因**：v0.5 改尺寸后未同步文案/注释。
- **修复后结果/验收**：zh/en 文案改为「靠近屏幕边缘时吸附」，注释更正。
- **类型**：文案 / 文档　**定位**：`i18n.ts:296,1161`、`commands.rs:1481`
- **优先级 P3　严重级别 Minor　状态**：待修复

## 三、待验证推断（不作结论，需真机确认）

1. Windows WebView2 与 macOS WKWebView 在 `start_dragging()` 原生拖动期间 `pointerup` / `click` 的派发时机不同，可能影响 PET-004 修复后的互斥窗口；本轮仅按「pointerup 可能丢失」设计超时兜底，**未做双平台实测**。
2. 互动模式解除穿透后，窗口级 hit-test 覆盖整个矩形（含透明留白），CSS 层缩小热区不能让桌面点击真正穿透；需原生全局鼠标钩子才能像素级穿透，本轮按已知限制保留。
3. `su-sleep.webp` 仍近似睁眼，靠降饱和 + 慢呼吸 + 灰色状态灯区分，真机观感待确认。
